RECADOODLE SERVER - DETAILED DEPLOYMENT GUIDE FOR A FRIEND
===========================================================

Repository:
https://github.com/matt3121/recadoodle2023

Last checked against the public main branch: 4 September 2026


IMPORTANT: READ THIS FIRST
--------------------------

Recadoodle is an experimental, unofficial replacement backend for preserved April 2023
Rec Room clients (build 20230414). It is not affiliated with or endorsed by Rec Room Inc.
It is not a general-purpose website and it is not a hardened production community service.
Use it with a small, trusted group first.

The public repository contains the server only. It does not contain a game client, game
binaries, a client patch, generated game assemblies, or private server data. Your friend
must use a legally obtained compatible client and a separately obtained compatible client
configuration method. Never point a modified client at the official live service, and do
not modify a normal live-game installation. Keep a separate backup of the preserved client.

This guide uses the supplied Docker Compose deployment and a Cloudflare Tunnel. This is the
recommended route because it:

  * keeps the Flask/Gunicorn port bound to localhost instead of the public Internet;
  * provides HTTPS at the public hostname;
  * avoids router port-forwarding in most home-hosting situations; and
  * keeps the SQLite database and uploads in a persistent Docker volume.

Cloudflare Tunnel only carries the HTTP/WebSocket server traffic. Photon Realtime and Voice
traffic are separate. A working Cloudflare Tunnel does not replace Photon.


WHAT YOUR FRIEND NEEDS
----------------------

1. A computer that can stay switched on while people use the server.
   Windows 10/11 with Docker Desktop, or a supported Linux host with Docker Engine and the
   Docker Compose plugin, is suitable. A VPS is also possible.

2. A 64-bit CPU, enough disk space for Docker plus future uploads/backups, and a reliable
   Internet connection. The project does not publish a formal minimum hardware size. Start
   small, monitor it, and do not assume endpoint tests guarantee high player capacity.

3. Docker with the modern Compose command. The command must be written as:

       docker compose

   It should not be the old standalone "docker-compose" program.

4. Git, or the ability to download and extract a ZIP from GitHub. Git is preferable because
   updates are much easier and safer.

5. A domain already added to a Cloudflare account. This guide uses play.example.com as the
   example hostname. Replace it everywhere with the real hostname.

6. A Cloudflare remotely managed Tunnel and its secret tunnel token.

7. Photon Realtime and Photon Voice application IDs created in your friend's own Photon
   account. Do not reuse somebody else's IDs.

8. A legally obtained April 2023 client (build 20230414) and a compatible way to configure
   its nameserver and Photon IDs. These are deliberately not distributed in this repo.


PART 1 - INSTALL AND CHECK THE PREREQUISITES
--------------------------------------------

Windows:

1. Install Git for Windows.
2. Install Docker Desktop and use Linux-container mode.
3. If Docker asks for WSL 2, install/enable it and reboot as instructed.
4. Start Docker Desktop and wait until it reports that the engine is running.
5. Open PowerShell. An ordinary user PowerShell window is normally sufficient.

Linux:

1. Install Docker Engine from Docker's official repository for the distribution.
2. Install the Docker Compose plugin.
3. Arrange permission to run Docker commands. Depending on the installation, commands may
   need sudo. If the account is added to the docker group, understand that membership is
   effectively root-level access to the machine.

Verify the installation:

    git --version
    docker version
    docker compose version

All three commands should complete successfully. If "docker version" cannot contact the
daemon, start Docker Desktop/service before continuing.

Official Docker Compose installation overview:
https://docs.docker.com/compose/install/


PART 2 - DOWNLOAD THE SERVER
----------------------------

Choose a private working directory that is not synced into a public Git repository. Then:

    git clone https://github.com/matt3121/recadoodle2023.git
    cd recadoodle2023

Confirm that these files exist in the current directory:

    compose.yaml
    Dockerfile
    .env.example
    manage.py
    DEPLOYMENT.md

If Git is unavailable, download the repository ZIP from GitHub, extract it, and open a
terminal in the extracted directory. ZIP installations can run the server but do not use
the Git update commands later in this guide.


PART 3 - CREATE THE PHOTON APPLICATIONS
---------------------------------------

Photon handles room networking and voice separately from this HTTP backend.

1. Sign in to the Photon dashboard using your friend's own account.
2. Create a Photon Realtime application. Copy its App ID exactly.
3. Create a Photon Voice application. Copy its App ID exactly.
4. A Chat App ID is optional for this deployment and can remain blank unless the compatible
   client configuration specifically requires one.
5. Keep the IDs private enough to avoid casual abuse, and make sure the exact same Realtime
   and Voice IDs are entered in both the server .env file and the client configuration.
6. Use the same Photon region expected by the client. The supplied default is "us". If a
   different region is deliberately selected, configure it consistently.

Do not confuse an App ID with a dashboard password, account secret, or Cloudflare token.
They belong in different fields.


PART 4 - CREATE THE CLOUDFLARE TUNNEL
-------------------------------------

Cloudflare currently describes this as a remotely managed tunnel with a published
application route.

1. Sign in to the Cloudflare dashboard.
2. Make sure the chosen domain is active in that account.
3. Go to Networking, then Tunnels.
4. Select "Create a tunnel".
5. Give it a recognizable name, for example "recadoodle-home".
6. Choose the Docker connector instructions.
7. Cloudflare will show a Docker command containing a long token. Copy only the token value
   after "--token". Do not run Cloudflare's standalone Docker command because this project
   already defines the cloudflared container in compose.yaml.
8. Treat that tunnel token as a password. Never paste it into Discord, screenshots, GitHub,
   support logs, or this guide.
9. Leave the Cloudflare page open. The connector will become healthy after Part 7.

Add the published application route when the dashboard allows it (it can also be added after
the connector starts):

  Subdomain/hostname:  play.example.com
  Service type:        HTTP
  Service URL:         http://backend:5000
  Path:                leave blank

The hostname must be the same hostname later placed in RECNET_DOMAIN. The origin must be
"backend:5000", not "localhost:5000". Inside the cloudflared container, localhost means the
cloudflared container itself; "backend" is the Docker Compose service name.

Cloudflare creates the tunnel DNS record when the published route is added. Do not add a
second conflicting A/AAAA/CNAME record for the same hostname.

Do not place a browser-interactive Cloudflare Access login, CAPTCHA, or challenge page in
front of the game API. The preserved game client cannot complete browser login challenges.
Use the existing authentication, a controlled user group, sensible Cloudflare security
rules, and network restrictions that do not inject interactive HTML into API requests.

Official Cloudflare tunnel instructions:
https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/

Cloudflare notes that tunnel connectivity may require outbound port 7844. No inbound router
port-forward is required for the tunnel deployment.


PART 5 - CREATE AND EDIT THE PRIVATE .ENV FILE
----------------------------------------------

From the repository directory, copy the example file.

Windows PowerShell:

    Copy-Item .env.example .env
    notepad .env

Linux:

    cp .env.example .env
    nano .env

Generate a unique JWT secret of at least 32 characters. If Python is installed locally:

    python -c "import secrets; print(secrets.token_urlsafe(48))"

If the command is called python3 on Linux:

    python3 -c "import secrets; print(secrets.token_urlsafe(48))"

Copy the generated output into JWT_SECRET. Generate it once, store it privately, and keep it
stable. Changing JWT_SECRET later signs everybody out and invalidates active sessions.

Use this as the production-style .env shape, replacing every placeholder:

    RECNET_DOMAIN=play.example.com
    SINGLE_HOST_MODE=true
    DATABASE_URL=sqlite:///recnet.sqlite3
    JWT_SECRET=PASTE_A_NEW_RANDOM_SECRET_HERE
    TOKEN_TTL_SECONDS=604800
    REFRESH_TOKEN_TTL_SECONDS=2592000
    STARTING_TOKENS=10000
    GAME_REWARD_TOKENS=100
    DAILY_GAME_REWARD_LIMIT=1000
    ALLOW_PASSWORDLESS_ACCOUNTS=false
    MIN_PASSWORD_LENGTH=12
    CORS_ALLOWED_ORIGINS=
    TRUSTED_HOSTS=play.example.com,localhost,127.0.0.1
    MAX_CONTENT_LENGTH=67108864
    MAX_FORM_MEMORY_SIZE=2097152
    MAX_FORM_PARTS=100
    RATE_LIMIT_ENABLED=true
    SESSION_COOKIE_SECURE=true
    PHOTON_REALTIME_APP_ID=PASTE_YOUR_REALTIME_APP_ID
    PHOTON_VOICE_APP_ID=PASTE_YOUR_VOICE_APP_ID
    PHOTON_CHAT_APP_ID=
    PHOTON_REGION=us
    TRUST_CLOUDFLARE_PROXY=true
    CLOUDFLARE_TUNNEL_TOKEN=PASTE_THE_TUNNEL_TOKEN

Rules for the important values:

  * RECNET_DOMAIN is only a hostname. Do not include https://, a trailing slash, or a path.
  * SINGLE_HOST_MODE=true is correct when every discovered service uses one public hostname.
  * DATABASE_URL should remain sqlite:///recnet.sqlite3 for the supplied Docker deployment.
  * JWT_SECRET must not be the example value and must not be shared.
  * STARTING_TOKENS is the balance assigned to newly created accounts.
  * GAME_REWARD_TOKENS is the token reward per accepted game-session identifier.
  * DAILY_GAME_REWARD_LIMIT is the maximum game-reward tokens an account can receive during
    one UTC day. It does not limit tokens already owned or received by other future systems.
  * ALLOW_PASSWORDLESS_ACCOUNTS should remain false on an Internet-accessible deployment.
  * RATE_LIMIT_ENABLED should remain true.
  * SESSION_COOKIE_SECURE should be true because users access the public API over HTTPS.
  * TRUST_CLOUDFLARE_PROXY should be true only when requests arrive through this trusted
    Cloudflare connector/reverse-proxy arrangement.
  * TRUSTED_HOSTS must contain the actual public hostname. Keep localhost and 127.0.0.1 for
    local checks.
  * CLOUDFLARE_TUNNEL_TOKEN is secret and must never be committed.

Save and close the file. Check that Git will ignore it:

    git status --short

The output must not list .env. Do not continue until that is true.


PART 6 - BUILD AND START THE BACKEND FIRST
------------------------------------------

Build and start only the backend:

    docker compose up -d --build backend

The first build downloads the Python base image and installs dependencies, so it may take a
few minutes. Inspect the result:

    docker compose ps
    docker compose logs --tail 100 backend

The backend should be "Up" and should not be continually restarting. The supplied mapping is
127.0.0.1:5000:5000, so it is reachable from the host but is not intentionally bound to every
network interface.

Check it locally.

Windows PowerShell:

    Invoke-RestMethod http://127.0.0.1:5000/healthz
    Invoke-RestMethod http://127.0.0.1:5000/readyz

Linux/macOS shell:

    curl -sS http://127.0.0.1:5000/healthz
    curl -sS http://127.0.0.1:5000/readyz

/healthz is process liveness. /readyz also runs a lightweight database query. A healthy
readiness response has HTTP 200 and reports that the database is "ok". Readiness does not
test Photon, room assets, database writes, or full gameplay.


PART 7 - START THE CLOUDFLARE CONNECTOR
---------------------------------------

Start the whole tunnel profile:

    docker compose --profile tunnel up -d --build

Inspect both services:

    docker compose ps
    docker compose logs --tail 100 backend cloudflared

Return to Networking > Tunnels in Cloudflare. The tunnel should become Healthy. If the
published application route was not added earlier, add it now using:

    Public hostname: play.example.com
    Service URL:     http://backend:5000

Now test the public URL in a browser or terminal:

    https://play.example.com/healthz
    https://play.example.com/readyz
    https://play.example.com/
    https://play.example.com/api/discovery

The root URL and discovery endpoint return JSON, not a normal HTML website. That is expected.
Discovered service URLs should all use the configured public hostname and HTTPS.

If the public URL returns 502, the usual cause is a route whose service URL says localhost
instead of backend, or a backend container that is stopped/restarting.


PART 8 - CREATE THE FIRST DEVELOPER ACCOUNT
-------------------------------------------

Run this from the repository directory while the backend is running:

    docker compose exec backend python manage.py create-developer --username FRIEND_USERNAME

The username must be 1-32 characters and unique. The command privately prompts for a password
and confirmation. Use a unique password of at least 12 characters. Nothing appears while the
password is typed; that is normal.

Record the printed account ID. On a new database, Coach is the system account at ID 1 and the
first created developer is normally ID 2. Coach has no published password and should not be
used for login.

The developer account is created with developer and moderator flags and receives the current
STARTING_TOKENS balance.

If another friend needs a developer account, run the command again with a different username
and password. Do not share one account/password between multiple people.


PART 9 - LINK THE ACCOUNT PICKER TO STEAM (WHEN NEEDED)
-------------------------------------------------------

Some compatible clients try to create an empty-password account during their loading flow.
The server rejects that intentionally. Create the password account first, then associate the
owner's platform identity with the password-required account picker.

For Steam, obtain the account owner's Steam ID64 and run:

    docker compose exec backend python manage.py link-platform --account-id 2 --platform 0 --platform-id STEAM_ID64

Replace 2 with the account ID printed in Part 8 and replace STEAM_ID64 with that same user's
own Steam ID64. Platform 0 is Steam. Although the command accepts platform values 0-5, this
public documentation does not define the others; do not guess them.

This link only selects an account in the picker. It is not Steam ticket verification and is
not proof that a request truly came from Steam. The user must still enter the server password.
Never link somebody else's platform ID without their permission.

Restart the client after linking.


PART 10 - CONFIGURE AND TEST THE CLIENT
---------------------------------------

In the compatible client configuration method, set:

    Nameserver/base server: https://play.example.com
    Photon Realtime App ID: the same PHOTON_REALTIME_APP_ID from .env
    Photon Voice App ID:    the same PHOTON_VOICE_APP_ID from .env
    Photon region:          the same region expected by the server/client setup

Exact patch-screen/file instructions are not in the public server repository, so this guide
cannot safely invent them. Follow the instructions belonging to the separately obtained,
compatible client configuration method.

Before launching:

  * back up the preserved client;
  * keep it separate from the official/live installation;
  * confirm the client build is 20230414;
  * disable client debug HTTP logging because it can expose passwords and bearer tokens; and
  * never configure the preserved client with real production credentials from another
    service.

Test in stages with only one client:

1. The client reaches the account picker/login flow.
2. The linked account appears and requires its password.
3. Login succeeds.
4. The Dorm Room loads.
5. Room matchmaking works.
6. Realtime player presence works.
7. Voice works.
8. Token balance appears.
9. A completed game reward changes the token balance once for that game session.
10. A token-priced store item purchase reduces the balance by the archived server price.

Only invite more people after all ten checks are acceptable.


PART 11 - HOW THE TOKEN SETTINGS WORK
-------------------------------------

The current server supports persistent game rewards and token-priced store purchases.

  * New accounts start with STARTING_TOKENS (default 10000).
  * A valid game reward request with a game-session identifier grants GAME_REWARD_TOKENS
    (default 100).
  * Repeating the same game-session identifier does not grant the reward twice.
  * Game rewards stop when DAILY_GAME_REWARD_LIMIT (default 1000) is reached for that account
    during the current UTC day.
  * Purchases use the prices in the server's archived storefront data.
  * If the client sends an old/stale expected price, the purchase is rejected.
  * The balance is debited atomically and cannot go below zero.
  * Unique avatar/equipment purchases are recorded so the same unique item is not purchased
    twice.
  * Token transactions and purchase receipts persist in SQLite.

To change reward values, edit .env, then recreate the backend container so it receives the
new environment values:

    docker compose --profile tunnel up -d --build --force-recreate backend cloudflared

Changing STARTING_TOKENS affects newly created accounts; it does not rewrite existing account
balances. Do not promise real-money value for these experimental server tokens.


PART 12 - NORMAL OPERATION COMMANDS
-----------------------------------

Show service status:

    docker compose ps

Follow live logs (press Ctrl+C to stop following; containers keep running):

    docker compose logs -f --tail 100 backend cloudflared

Restart only the backend:

    docker compose restart backend

Stop the stack but preserve the database volume:

    docker compose --profile tunnel down

Start it again:

    docker compose --profile tunnel up -d

Rebuild after configuration/code changes:

    docker compose --profile tunnel up -d --build

IMPORTANT: Do not run "docker compose down -v". The -v option removes the recnet-data volume
and can erase accounts, saves, uploads, purchases, token history, and other persistent data.


PART 13 - CREATE AND COPY A VERIFIED BACKUP
-------------------------------------------

The server includes an online SQLite backup command. It can run while the server is online:

    docker compose exec backend python manage.py backup-database

The command prints a timestamped path similar to:

    /app/instance/backups/recadoodle-20260904-183000.sqlite3

List completed backups:

    docker compose exec backend ls -lh /app/instance/backups

Copy a specific backup out of Docker, replacing the timestamp with the real filename:

    docker compose cp backend:/app/instance/backups/recadoodle-YYYYMMDD-HHMMSS.sqlite3 .

The backup uses SQLite's online backup API, runs quick_check, and refuses to overwrite an
existing destination. A backup left only inside the same Docker volume is not sufficient.
Copy it to a separate encrypted disk or other private backup location.

Backups contain account and authentication data. Treat them as secrets. Never commit one,
upload it to a public file host, or post it in a support channel.

Also make a protected backup of .env. A database backup without the correct stable settings
and JWT secret may not provide a smooth recovery.

Test the recovery procedure on a separate machine/container before relying on backups. Stop
the backend before manually replacing the live SQLite file. File ownership inside the volume
must remain writable by the container's recnet user (UID 10001). If your friend is not
comfortable restoring Docker volumes and ownership, get help before a real outage rather
than improvising against the only copy of the database.


PART 14 - UPDATE THE SERVER SAFELY
----------------------------------

For a Git clone, first enter the repository directory and confirm there are no unexpected
local code edits:

    git status --short

The private .env should not appear. If other files appear, do not discard them blindly.
Understand or back them up first.

1. Create and copy out a verified database backup using Part 13.
2. Read the public repository changes/release notes before applying them.
3. Download reviewed changes without creating a merge commit:

       git pull --ff-only

4. Rebuild and recreate the services:

       docker compose --profile tunnel up -d --build

5. Check status, logs, liveness, readiness, discovery, login, Photon, and a store/reward flow.

Database tables are created automatically at startup when missing. That is not a substitute
for a backup, especially when future changes alter persistent data.


PART 15 - SECURITY CHECKLIST
----------------------------

Before inviting anyone, confirm all of the following:

  [ ] .env is not tracked by Git and has never been posted publicly.
  [ ] JWT_SECRET is unique, random, and at least 32 characters.
  [ ] CLOUDFLARE_TUNNEL_TOKEN has not been shared.
  [ ] Account passwords are unique and at least 12 characters.
  [ ] ALLOW_PASSWORDLESS_ACCOUNTS=false.
  [ ] RATE_LIMIT_ENABLED=true.
  [ ] SESSION_COOKIE_SECURE=true for the HTTPS deployment.
  [ ] TRUSTED_HOSTS contains the real public hostname.
  [ ] The backend port remains bound to 127.0.0.1 in compose.yaml.
  [ ] No router port-forward exposes TCP 5000.
  [ ] No interactive Cloudflare Access/challenge page is in front of the game API.
  [ ] Client debug HTTP logging is off.
  [ ] The preserved client is separate from the official live installation.
  [ ] Backups have been copied off the Docker volume and protected.
  [ ] The server is being used only with a small, controlled test group.

The supplied Gunicorn command deliberately uses one threaded worker because notifications
and rate-limit state are process-local. Do not increase the worker count or create multiple
backend replicas unless the application is first changed to use shared state.


PART 16 - TROUBLESHOOTING
-------------------------

Problem: "docker" is not recognized.
  Install/start Docker Desktop or Docker Engine, close and reopen the terminal, and re-run
  "docker version" and "docker compose version".

Problem: The backend container repeatedly restarts.
  Run:

      docker compose ps
      docker compose logs --tail 200 backend

  Look for malformed .env values, an invalid integer, missing files, or volume permissions.

Problem: Cloudflare shows the tunnel as Inactive/Down.
  Confirm CLOUDFLARE_TUNNEL_TOKEN contains only the token, then run:

      docker compose --profile tunnel up -d cloudflared
      docker compose logs --tail 200 cloudflared

  Confirm outbound connectivity, including Cloudflare tunnel traffic on port 7844 where the
  network restricts outbound connections.

Problem: Public hostname returns 502 Bad Gateway.
  Confirm the published route origin is exactly http://backend:5000 and that the backend is
  Up. Do not use localhost:5000 as the origin inside the cloudflared container.

Problem: Public hostname shows Cloudflare error 1016.
  The DNS route points to a tunnel that is not available. Check tunnel/container health and
  ensure the published route belongs to the intended tunnel.

Problem: /healthz works but /readyz returns 503.
  The process is alive but its database query failed. Inspect backend logs and the Docker
  volume. Do not delete/recreate the volume as a first troubleshooting step.

Problem: Root/discovery JSON contains localhost or the wrong hostname.
  Correct RECNET_DOMAIN and TRUSTED_HOSTS in .env, then recreate the services:

      docker compose --profile tunnel up -d --build --force-recreate

Problem: No web page appears.
  Expected. This is an API backend. Use /healthz, /readyz, /, and /api/discovery for checks.

Problem: Login fails.
  Confirm the account was created, the password is correct, and the platform link uses the
  correct account ID and the same user's own Steam ID64. Inspect safe rejection categories in
  the access log; never enable raw request-body logging or share access/refresh tokens.

Problem: Client loading flow tries to make an empty-password account.
  Keep ALLOW_PASSWORDLESS_ACCOUNTS=false. Create a developer account with manage.py and link
  the platform identity as described in Parts 8 and 9.

Problem: Client reports a version mismatch or routes behave strangely.
  Confirm the client is the intended April 2023 build 20230414. Newer clients are not covered
  by this backend's compatibility target.

Problem: Rooms work but voice does not.
  Recheck that a Photon Voice app was created and that its exact App ID is in both .env and the
  client. Realtime, Voice, HTTP, and room assets are separate failure areas.

Problem: Matchmaking/rooms do not work, but HTTP login works.
  Check the Photon Realtime App ID, region, client configuration, and compatible room assets.
  A healthy /healthz endpoint does not prove Photon is correctly configured.

Problem: Token reward does not appear.
  The request needs a game-session identifier, the same identifier is only rewarded once, and
  the account may have reached DAILY_GAME_REWARD_LIMIT for the current UTC day.

Problem: A store purchase is rejected.
  Check the account balance, whether the item is token-priced, whether a unique item is already
  owned, and whether the client's expected price is stale compared with archived server data.

Problem: Changes to .env have no effect.
  "docker compose restart" does not always apply changed environment configuration. Recreate
  the services with:

      docker compose --profile tunnel up -d --build --force-recreate

Problem: Disk usage keeps growing.
  Check Docker disk use, uploads, and backups. Copy backups off-host and apply a deliberate
  retention policy. Do not delete unknown files from the live volume while the server runs.


PART 17 - FINAL HANDOFF INFORMATION TO RECORD PRIVATELY
-------------------------------------------------------

Your friend should privately record:

  * the server machine and operating system;
  * the local path of the Git checkout;
  * the public hostname;
  * the Cloudflare account and tunnel name (not the token in ordinary notes);
  * the Photon account and the names of the Realtime/Voice apps;
  * the developer account IDs and owners (not plaintext passwords);
  * the most recent verified backup date and off-host location;
  * the current Git commit from "git rev-parse HEAD"; and
  * who is allowed to administer the host.

Do not put secrets into this text file. Keep .env and recovery details in an appropriate
password manager or encrypted storage.
